## 1. 执行摘要

StudyTrace 面向正在自学课程、技能或职业能力的个人。它不继续增加“课程内容”，而是帮助用户把学习目标变成今天可完成的任务，并为每次完成保留一条证据，最后通过周复盘看到自己真正做了什么。

第一版采用本地优先、无需注册的 Web 应用，降低首次使用门槛。商业验证重点不是立刻收费，而是确认用户是否愿意持续记录“任务 + 学习证据 + 周复盘”。如果这个闭环成立，再验证跨设备同步、AI 复盘和学习小组等付费能力。

## 2. 业务背景与问题

自学者常使用视频课程、文章、笔记和待办工具，但这些工具分别解决“内容获取”“知识记录”或“任务提醒”，没有形成学习成果闭环。常见问题包括：

- 目标过大，用户不知道今天具体做什么。
- “看完了”被当成“学会了”，没有输出或练习证据。
- 学习中断后难以恢复，不知道从哪里继续。
- 周末只能凭感觉评价进度，无法判断时间花在了哪里。
- 通用待办工具缺少学习语境，课程、练习、作品和复盘彼此分散。

## 3. 目标用户

### 核心用户

18–35 岁、正在通过线上课程或自主项目学习一项技能的个人学习者，每周计划投入 3–10 小时，主要使用手机或个人电脑。

### 首批场景

- 学习编程并完成一个作品。
- 准备职业证书或语言考试。
- 跟随视频课程完成练习。
- 用 4–8 周掌握一项可展示的新技能。

### 非目标用户

- 需要班级管理、成绩排名和教务功能的学校。
- 需要复杂项目依赖、工时和多人协作的企业团队。
- 只想消费课程内容、不愿记录任何学习行为的用户。

## 4. 业务价值主张

> 让每一次学习都留下可以回看的进展证据。

对用户的价值：

1. 把模糊目标转成可执行的短任务。
2. 用链接或文字记录学习输出，而不是只记录观看时长。
3. 在中断后快速找到下一步。
4. 通过周复盘形成持续改进，而不是依赖打卡焦虑。

对业务的价值：

1. 验证“学习证据闭环”是否形成持续使用习惯。
2. 为后续同步、AI 反馈、模板市场和学习小组建立数据结构。
3. 以低基础设施成本获得第一批可访谈用户和真实使用证据。

## 5. 业务目标与衡量指标

以下数字是 MVP 的验证目标，不是现有市场事实。

| 目标 | 指标定义 | 试运行目标 |
|---|---|---:|
| 用户理解核心价值 | 首次访问后 24 小时内创建目标、完成任务并添加证据 | 激活率 ≥ 45% |
| 形成短期使用习惯 | 激活用户第 7 天仍有记录行为 | W1 留存 ≥ 30% |
| 证据机制有价值 | 已完成任务中包含证据的比例 | ≥ 50% |
| 复盘机制可用 | 活跃用户完成当周复盘的比例 | ≥ 35% |
| 产品不制造额外负担 | 用户完成一次任务记录的中位操作时间 | ≤ 30 秒 |

试运行建议招募 20–50 名自学者，持续 2–4 周。样本只用于方向验证，不用于声称市场规模或统计显著性。

## 6. 商业模式假设

MVP 免费且无需账号，先验证留存。若核心指标达到目标，再测试：

- 免费版：本地目标、任务、证据和周复盘。
- 个人订阅：跨设备同步、AI 周报、历史趋势和高级模板。
- 小组版：教练/学习伙伴反馈、共享里程碑和小组复盘。

本阶段不接支付、不承诺价格，也不收集支付信息。

## 7. MVP 业务范围

### 包含

- 最多 3 个进行中的学习目标。
- 为目标创建有预计时长的学习任务。
- 今日任务列表与任务完成。
- 完成时添加文字或 URL 证据。
- 本周进度和周复盘。
- JSON 数据导入、导出和本地清空。
- 移动端和桌面端可用。

### 不包含

- 登录、云同步、多人协作、排行榜。
- AI 自动拆解目标或评价学习质量。
- 文件上传、音视频托管、消息推送。
- 课程售卖、支付和证书。
- 原生 iOS/Android 应用。

## 8. 关键业务规则

1. 一个用户最多同时保留 3 个进行中目标，归档后可创建新目标。
2. 任务可以完成而不添加证据，但界面要提示证据的价值，不得强制。
3. 证据只接受纯文本和 `http/https` 链接，不上传文件。
4. “学习连续天数”不作为核心指标，避免为了保持数字而产生低质量打卡。
5. 周从用户本地时区的周一开始，周日结束。
6. 所有数据默认只保存在用户浏览器；清除浏览器数据可能导致丢失，产品必须明确提示并提供导出。

## 9. 业务流程

1. 用户创建一个 4–8 周学习目标。
2. 用户创建若干小任务，并给任务安排日期和预计时长。
3. 用户每天打开“今天”，选择任务并完成。
4. 用户为完成记录补充练习链接、作品地址或文字总结。
5. 用户在周末查看完成情况并填写周复盘。
6. 用户据此调整下周任务，直到目标完成或归档。

## 10. 风险与对策

| 风险 | 影响 | MVP 对策 |
|---|---|---|
| 记录成本高于获得的价值 | 用户很快流失 | 完成记录控制在 30 秒内；证据非强制 |
| 本地数据被清除 | 用户失去信任 | 首次说明、周期提醒导出、提供 JSON 备份 |
| 与普通待办工具差异不明显 | 激活率低 | 突出学习证据和周复盘，不扩张通用待办功能 |
| 用户沉迷打卡数字 | 偏离学习成果 | 不提供排行榜和连续天数主指标 |
| URL 证据包含隐私信息 | 隐私风险 | 不自动抓取 URL 内容；明确数据只在本地保存 |

## 11. 资源与里程碑

| 周次 | 目标 |
|---|---|
| 第 1 周 | 需求冻结、技术选型、信息架构和视觉方向 |
| 第 2 周 | 目标、任务、今日列表和本地持久化 |
| 第 3 周 | 证据、周复盘、导入导出和可访问性 |
| 第 4 周 | 回归测试、上线手册、小范围发布和验证 |

建议最小团队：1 名产品/业务负责人、1 名全栈开发者、兼职设计与测试支持。产品工厂 Agent 可以承担文档推导、代码生成和部分验证，但不能替代四个人工负责人决策。

## 12. 立项与停止条件

### 进入开发

- BRD 和 PRD 的范围、非目标及指标得到业务负责人确认。
- 第一版不收集敏感个人信息、不接支付的边界得到确认。
- 有至少 5 名目标用户愿意参加可用性测试。

### 停止或调整

- 目标用户不愿添加任何学习证据。
- 证据记录导致明显的额外压力或虚假打卡。
- 小范围测试表明普通待办工具已能完整替代核心价值。
- 本地优先模式无法建立足够信任，且团队无能力承担账号与同步成本。
